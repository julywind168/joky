# 有状态服务的编程模型与实施计划

状态：2026-10-23，S0–S4 已完成实现与 Debug 验收。以 `examples/chat.jk` / `chat_logic.jk` 为验收对象，
目标是降低业务开发者必须理解的概念数量。阶段交付与验证记录见末节。
当前接口仍以 [language.md](language.md) 为准，状态与 ABI 不变量见
[architecture.md](architecture.md)。本文承接[状态域设计](server-concurrency.md)、
[状态域语法](state-domain-syntax.md)和[热更新计划](aot-script-hot-reload.md)，不复制其现行规范。

## 1. 问题与目标

聊天室的业务对象是连接、账户、房间和命令，但实现还要求作者组织状态 Owner、目录、
请求根、就绪邮箱、终止邮箱、永久持有任务、快照、候选、批次和提交回执。
其中一部分是保证正确性所需的运行时机制，不应都成为实现一条业务命令的前置知识。

保留现有能力：受检状态、唯一所有者与弱句柄、完整读取依赖验证、独立候选、
状态与消息原子入队、结构化取消和兼容代码发布。面向业务的默认模型收敛为：

1. **状态归属**：作用域或容器拥有状态；句柄仅用于访问，关闭所有者取消关联工作。
2. **业务操作**：读取、条件检查、状态修改和待发送消息组成一次可提交操作。
3. **异步流程**：网络和文件 I/O、等待与连接协议在操作外执行。

验收看开发者必须维护的协议，不以代码行数作为唯一指标。收费规则应在一次业务操作内可读；
换房应明确涉及账户、旧房间和新房间；连接策略不应要求业务作者编写候选提交协议。

## 2. 用两种业务检验目标模型

### 2.1 发言

以下是目标写法，`text` 代码块不是当前可执行语法。`broadcast` 只登记待提交消息，
不能直接操作 socket。片段省略账户与房间句柄的解析代码；实现仍须显式解析，
再在完整读取集合中验证账户仍属于该房间，不能遗漏这一依赖；发生变化时重新解析并开始新的尝试。

```text
when "say" (mut account, room) {
    if account.balance_cents < 100 {
        Err(ChatError.InsufficientBalance)
    } else {
        account.balance_cents -= 100
        room.broadcast(message(account.id, text))
        Ok({})
    }
}
```

成功将扣费与所有消息一起发布；业务拒绝、容量不足、关闭或冲突均不发布部分结果。
网络送达不是此提交的保证，仍允许已入队消息因断线而无法送达。

### 2.2 换房

解析账户、旧房间和目标房间后，一次操作验证旧成员关系，移出旧房间、加入新房间、
更新账户，并按顺序登记离开和加入通知。首次加入、重复加入、同一房间别名、
解析期间并发换房以及目标房间创建都须有明确路径。

目录解析和新房间创建有独立生命周期，不允许伪装成可无限重放的纯事务体。
第一版保持显式读取集合，不承诺通用自动依赖发现或在事务中动态取得任意活根引用。
发言与换房都能表达后，才冻结便捷接口，避免只优化计数器一类单域示例。

## 3. 状态所有权交接

宿主作用域创建有界状态容器，脚本用短初始化流程建立状态，并将唯一 Owner 移交给容器。
交接完成后初始化流程返回，状态无需依靠永不完成的 continuation 存活。
容器关闭或移除条目时关闭对应域，既有弱句柄失效，域任务按现有协议取消。

第一阶段优先复用目录的键、查找、容量、执行器身份和条件删除能力，增加**显式拥有的条目**，
不改变普通弱路由插入的行为。具体命名在实现时确定，并写入语言参考。

- 交接是所有权消费，成功后原包装不再关闭域，不得出现双所有者。
- 失败、取消及交接前后清理均须明确；失败不得泄漏域或留下未声明的永久所有者。
- 容器操作不得在持有注册表可变借用时析构域或取消任务，避免清理重入。
- 条件删除必须比较域身份，旧连接清理不能删除后来复用相同业务键的新条目。
- 容器只拥有根及其当前实现所需的代码；不为所有权额外保留初始化流程的模块。
- 容器关闭与执行器关闭按既有清理协议释放根、请求、消息和预算。
- 代码发布期间的旧流程仍可能创建旧版根。交接能力本身不等价于自动追上新版；
  在统一创建/发布协议完成前，示例保留必要的显式发布屏障，不能直接删除校验。

账户归连接生命周期，房间归服务生命周期。空房间回收是显式服务策略，不能通过
悄悄改变目录弱引用或句柄保活规则实现。连接异常退出后的局部清理与失败隔离随后接入。

## 4. 统一业务操作的提交语义

目标是让面向业务的 `when` 及句柄方法走同一套候选提交规则；现有原地短操作保留为
明确的底层能力。这是语义调整，不能只增加别名就声称已经完成。

目标规则：

- 一次尝试在冻结状态上计算，写入独立候选；活根引用不跨挂起点。
- 操作体正常成功才申请提交。返回业务 `Err` 丢弃候选；`Ok(false)` 是成功业务结果，
  不能靠 false 隐式表达回滚。普通非 Result 结果与业务 Result 的规则须在切换前统一。
- 消息暂存在操作所属的有界批次中；登记消息计入预算，容量检查和状态发布原子完成。
- 操作体不执行网络、文件、随机宿主效果或用户清理钩子，不能隐式重放外部副作用。
- 业务拒绝与运行时的关闭、资源不足、冲突、入口不兼容保留区别；错误包装方式在实现阶段
  与现有 Result 类型规则一起确定，不通过 `!` 将常见拒绝统一升级为服务失败。
- 只对完整、可重新计算的尝试提供有界重试；达到次数/截止时间限制后返回错误。
  动态房间解析也须进入重试边界，不能只在固定旧句柄上重复执行。
- 当前冻结是深复制。便捷接口必须继续计算临时峰值并执行预算检查；不承诺零复制，
  写时复制与性能优化另行验证。

实现可复用快照、候选集合、读取凭据与 outbox；多域候选编辑、受检消息效果和拥有值捕获
需要编译器支持。String 捕获、返回及句柄方法参数已经能够执行，不能将其重复列为待实现能力。
参考文档中与现有实现不符的纯值限制须随相应能力核实后修正。

## 5. 热更新与契约边界

一次业务操作尝试固定其实现及所需代码所有者，条件、计算与消息构造不在同一次尝试中
切换版本。发布使旧尝试的凭据失效时，重新选择当前实现、解析依赖并开始新的尝试。
网络接收等旧流程可以继续运行，通过稳定操作身份进入下一次业务操作。

编译器提取的具名操作身份与捕获契约可复用；普通外层流程中的旧 `plan` 不能被当作
已经更新的业务计算。多个参与域和导入模块的版本兼容必须整体验证，不靠同名或槽数猜测。

宿主声明所需入口及完整类型契约，编译暂存版本后，在切换入口与域代码之前一起校验。
缺失入口、参数/返回值变化或不兼容 schema 拒绝发布并保留旧版。
共享契约应只有一个源定义，避免宿主和脚本手工复制记录并靠字符串维持约定。

此阶段不迁移挂起栈、不自动迁移变化的状态布局，也不保证外部效果 exactly-once。

## 6. 可复用的连接运行策略

标准库组件承接读写竞速、发送队列、断开清理、局部失败边界和慢客户端处理。
业务提供建立连接、处理命令和移除成员的操作；队列容量、超限行为、空闲回收及重试预算
仍由调用方配置。先以 chat 验证复用边界，不增加只适用于聊天室的语言原语。

慢客户端淘汰应采用有界工作队列/迭代流程。淘汰产生的离开通知仍有明确顺序和容量策略，
不能通过递归淘汰把一次失败扩展成无界请求栈。局部错误转换为可处理结果，
单个连接或房间失败不默认传播为整个服务失败。

### S2 的增量交付

S2a 先统一 `when` 和句柄方法的候选执行：完整集合深复制，成功才发布，标准顶层 Result.Err
丢弃候选，Ok(false) 与普通 false 都正常发布；算术异常不再隔离域，资源不足不发布候选。
结果仍是外层 DomainAccessError 与内层业务结果，不扁平化两类错误。显式原地短操作保留旧规则。
一次尝试在一个同步 FIFO 轮次中完成，固定执行模块且不允许宿主效果，因此复制后至发布前不会有
并发状态或代码变化；不为这种尝试增加无意义的重试循环。跨轮次依赖解析仍由后续步骤处理。

随后 S2b 接入受检消息登记与统一提交拒绝，S2c 将发言／换房移入业务块，并让动态句柄解析进入
有界重算边界。S2a 不代表已经完成聊天业务表达验收，也不提前声称消息与状态原子发布。
