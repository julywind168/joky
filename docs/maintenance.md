# 文档维护约定

## 选择位置

- 当前语言行为放入 `lang/`；用户可调用的标准库 API 放入 `stdlib/`。
- 编译阶段、内部表示与链接契约放入 `compiler/`；调度、内存、native 交接与 ABI 放入 `runtime/`。
- 可复用的测试方法放入 `testing/`；带日期和版本的测试结果放入 `archive/reports/`。
- 尚未实施或部分实施的方案放入 `plans/`；已完成的原始计划放入 `archive/plans/`。

每个目录的 README 列出主题入口。文件名使用小写连字符，不给当前文档加阅读顺序或阶段编号；归档可以保留历史 phase 名称。目录 README 是文件名大小写的例外。

## 维护一份主要说明

每项行为选择一篇主要契约文档。其他页面用简短说明与链接导航，不复制整套 API 签名或状态表。用户的资源与取消语义仍属于 API 文档；锁、队列、token 和布局细节属于实现文档。

当前文档描述已经实现的范围，并标明不支持的边界；未来候选 API 不得混在当前签名列表中。设计草案明确写出状态、范围、前置依赖与验收条件。历史报告记录日期、commit、平台、工具链、运行方法和证据限制。

## 完成与归档

1. 核对实现及测试，把现有行为写入对应的语言、标准库或内部契约文档。
2. 将仍未完成的事项链接到活跃计划或待办，不用归档隐藏未勾选项。
3. 将原设计或验收记录移入 `archive/`，页首标注历史语境，并链接当前说明。
4. 保留原日期、数值和结论；后续结果另写报告，不能把旧测试数量当作当前状态。

## 移动与拆分

同步更新文档、根 README、贡献指南和源码注释里的引用，包括章节锚点。纯移动不改示例代码；拆分时核对代码块与内容完整性。目录入口面向读者，不按开发阶段罗列全部文件。

大型参考文档优先按可独立查询的主题拆分；每篇提供相关主题链接。不要为每个小语法点建立孤立页面。

## 检查

从仓库根目录运行：

```bash
python3 scripts/check-docs.py
git diff --check
```

检查器覆盖根目录、`docs/` 和 `examples/` 中的 Markdown，校验本地链接的文件与章节目标、代码围栏，以及 `docs/README.md` 对全部文档、`examples/README.md` 对示例源码与说明的可达性。不访问外链，不执行代码块，不证明技术内容与实现一致；修改示例或命令时仍需针对性实跑。
