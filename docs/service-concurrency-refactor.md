## 1. 现状评估

### 1.1 已经成立的部分

- **宿主与脚本分工**：宿主只负责 I/O、生命周期与并发骨架；业务全部在 Script。
  `main` 用 `race`／`scope`／`branch` 写出的服务骨架清晰。
- **契约单源与发布前预检**：`chat_contract.jk` 与 `require_contract` 让热更新边界明确。
- **多资源 `when`**：`when "say" (mut account, room)` 让收费规则在一次业务操作内可读；
  换房的三方写集合一眼可见。这是本组合最有辨识度的部分，重构保留它作为核心。
- **所有权归属**：账户归连接，房间归服务；重试、淘汰均有上限。
- **多线程底座**：TP0–TP10 已交付转移资格推导、受检任务包、冻结代码共享与保活、
  任务状态机、私有分片与共享预算、取消检查点和关闭协议，可复用于服务端。

### 1.2 协议负担

R0／R1 实施前，`chat_logic.jk` 约 490 行，真正的业务规则（扣费、加入／离开、消息格式）约 150 行，
其余为协议与样板。业务作者实际接触的概念包括 Owner、目录、请求根、就绪邮箱、停止邮箱、
发布屏障、重试、排除列表、`Attempt` 双层 Result 等十余项。主要来源：

| 负担 | 表现 | 根因 |
| --- | --- | --- |
| 慢客户端淘汰 | `excluded` 参数穿过 say／join／leave／reply／enter／depart／deliver／broadcast；`run_command`、`retry_command`、`slow_client`、`target_member` 约 100 行 | 收件人队列容量参与业务提交，一个慢连接可让他人的操作失败 |
| 取得或创建房间 | Catalog 四态、等待者邮箱、请求邮箱、`next_room`／`init_room`／`open_room`／`fail_room`、`refresh` 屏障，约 120 行；宿主 `create_room`／`manage_rooms` 固化创建步骤 | 域不能在 `when` 内创建；宿主承担了业务流程，修改创建流程需重编宿主 |
| 手写位置校验 | `expected` 参数、`Retry.Changed`、64 次重试循环 | 访问集合依赖状态（账户 → 所在房间），需在 `when` 外解析 |
| 捕获仪式 | 每个操作先 `text.clone()`、`copy_ids(excluded)` | `when` 捕获须为拥有值，缺少派生 Clone |

### 1.3 已核实的语言与实现限制

以下为 R0／R1 实施前由 Debug 探针与源码核对确认的基线；前三项已在 R1 解除，
循环清理已在 R0 完成。当前能力以语言参考为准，其余并发限制留待后续阶段：

- 挂起函数内不能消费式解构拥有记录（`Owned record destructuring requires a synchronous function`），
  chat 因此需要 `split`、`split_request`、`split_work`、`split_room` 四个辅助函数。
- 无派生 Clone（`Command.clone` 手写），Array 无 clone／contains（`copy_ids`、`contains` 手写）。
- 枚举不支持 `==`，`match status { Pending => true, _ => false }` 重复出现。
- `for x in &array`／`&mut array` 与 `if let` 已可用；chat 中约十处手写下标循环属于示例债务。
- 事务候选 `Candidates::capture` 对访问集合中每个域执行完整快照，不区分读写；
  只读的 Room 也被复制。
- `--task-workers N` 下 chat 整体被拒：子任务包含引用；仅含 `join` 与 `println` 的程序也被拒，
  原因是 `println` 未声明 ParallelSafe。`session.run` 接收函数值回调，
  而间接目标当前缺少线程证据，同样会被拒。

## 2. 目标组合

### 2.1 前沿方向的收敛

| 语言／系统 | 状态单位 | 数据竞争安全 | 可借鉴点 |
| --- | --- | --- | --- |
| Verona | cown，`when` 多资源获取 | 区域所有权 | 多资源原子行为；`when` 即消息，无 channel |
| Pony | actor | 引用能力 | 编译期竞争自由 |
| Erlang／Elixir | 进程 | 不可变数据、独立堆 | 监督树、热更新与 `code_change` |
| Swift 6 | actor | Sendable、区域隔离推导、`sending` | 推导减少标注；actor 重入是反例 |
| Haskell STM／Clojure | TVar／ref | 不可变 + 事务 | Clojure 在 `dosync` 内发送 agent 消息，提交后才投递 |
| OCaml 5／Koka／Unison | — | — | 代数效应统一“代码能做什么” |
| Roc | — | 纯函数 | 平台／应用分离，与 AOT 宿主 + Script 同构 |
| FoundationDB／TigerBeetle | — | 单线程 | 确定性仿真与重放 |

收敛为五层：结构化并发；编译期推导的数据竞争自由；共享状态单位（actor 为主流，
多对象原子操作由 BoC 或 STM 补足）；效果约束；热更新、监督与确定性重放等运维能力。

### 2.2 Joky 的选择

1. **结构化并发**：保留 `scope`／`branch`／`join`／`race`，补监督策略。
2. **`when` 是唯一共享状态原语**：BoC 调度 + 事务语义；访问集合可依赖状态（D3／D4）；
   不等待结果的需求用 `branch { when … }` 表达，只有程序顺序入队另行定案（D6）。
3. **提交后生效的效果**：发送消息、创建域、登记定时器统一暂存，到提交点才发布。
   outbox 退为运行时内部机制。
4. **转移资格由编译器推导**：沿用 Transfer／Share，暂不开放用户可写 trait。
5. **效果标注逐步统一**：`@suspends`、事务内允许的效果、ParallelSafe 收敛到一套内部分类。
6. **按调用切换代码的热更新**：保持现状。语言参考已有显式状态迁移与多域批次迁移，
   多线程下的适配由第 4 节运行协议承担。
7. **确定性模式**：Local 执行器 + 可配置种子的调度顺序，用于重放与多线程阶段的验证。

差异化定位是 **BoC 多资源原子操作 + 提交后生效的效果 + 按调用热更新** 的组合：
Verona 有 BoC 而无热更新与事务效果，Erlang 有热更新而无多 actor 原子操作。

目标是业务作者只需理解五个概念：任务作用域、状态（`#state`）、`when`、会话、提交后效果。

## 3. 设计决策

各节的“示意”代码块使用 `text`，不是当前可执行语法，名称未冻结。

### D1 收件人容量与提交解耦（契约变更）

**R2 前契约（Reject 仍保留）**：提交一次检查全部目标容量；任一目标关闭或容量不足返回
`OutboxClosed`／`OutboxFull`，所有根和消息均不发布；成功时根与全部目标消息在同一无挂起区间
发布（见语言参考的出站信箱章节）。这保证的是**状态与全部目标消息在内存中联合入队**，
与网络是否送达无关。

**R2 契约**：队列在创建时声明溢出策略。

| 策略 | 提交时遇到满／关闭 | 用途 |
| --- | --- | --- |
| `Reject` | 保留现行语义：整体拒绝，不发布任何根与消息 | 必须与状态联合入队的控制消息 |
| `Disconnect` | 提交照常成功；本次提交发往该目标的消息全部不入队，目标标记溢出并断开 | 事件流，chat 业务输出 |

状态同步流所需的 `KeepLatest`（保留最新）不纳入 R2。定案前须回答一次提交含多条消息时
如何替换、单批超过目标容量如何处理、目标已关闭时如何处理，见第 9 节。

选用 `Disconnect` 即接受**“状态已提交、部分收件人未收到本次消息”**，
这是对联合入队保证的明确放宽，须写入语言参考，而不是视为既有保证的推论。
同一目标在一次提交内的消息要么全部入队、要么全部不入队，不出现单目标内的部分消息。
批次自身的条数与字节预算仍按现有 DomainLimits 检查，超限为 ResourceLimit。

**混合目标的协调**：一次提交可能同时包含 `Reject` 与 `Disconnect` 目标。

- 所有拒绝条件（含全部 `Reject` 目标的容量与关闭状态）确定之前，不得公开任何消息，
  也不得触发任何 `Disconnect` 目标的溢出处理；否则可能先断开一个连接，随后又因
  `Reject` 目标失败而回滚事务。
- 只含可丢弃目标（`Disconnect`）的提交，可逐目标以原子批次投递，不需要跨目标预留。
- 含 `Reject` 目标的提交必须保证检查到发布之间容量不被他人占用。Local 模式下检查与发布
  位于同一同步执行轮次，现有实现已满足；多线程模式需要容量预留、统一提交锁或等价协议。
  一种候选是把 `Reject` 目标作为 BoC 资源纳入访问集合，在独占授权下检查容量；
  具体方案在第 4 节运行协议中确定。
- chat 的常用路径只用 `Disconnect`，可享受无协调的投递；保留 `Reject` 强语义的场景
  仍须承担相应协调成本。

**提交点**：验证完成并进入发布区间即为提交点。

- 提交点之前：业务 Err、异常、资源不足、取消一律丢弃候选与全部消息。
- 提交点之后：取消或调用方离开不撤销已公开的状态与消息，只停止后续工作。
- 溢出处理发生在发布区间内，只改变目标的溢出标记，不使提交失败，也不分配可能失败的资源。

**溢出通知必须走独立路径**：不能依赖已满的消息队列。写任务可能正阻塞在 TCP 写入，
因此运行时须通过不受容量限制的关闭／取消信号唤醒会话。现有 `session.run` 已在 `race` 中
独立等待 control 邮箱，规格要求溢出时**关闭** control（或等价取消信号）而非向其投递消息，
由 `race` 取消阻塞的写分支，再按普通断线路径清理成员关系。

**收益**：chat 业务签名移除 `excluded`，删除淘汰工作表与重放；只含 `Disconnect` 目标的提交
在多线程下无需跨队列预留（见 D7）。

**迁移**：`Reject` 队列保留 `OutboxFull`／`OutboxClosed` 及 `failed_outbox`，相关测试不变；
chat 改用 `Disconnect` 后，“满队列整体回滚”的断言改为“提交成功、溢出连接被断开、
其他成员正常收到、断开连接的成员关系被清理”。

### D2 统一提交后效果

`when` 内允许的外部效果统一为暂存效果：发送消息、创建域（D3）、登记定时器。
提交点之前的所有失败与取消丢弃全部暂存效果；提交点之后不撤销（D1）。
用户不再创建 outbox、传递 Handle 或比较 `identity()`；会话提供 `conn.send`，
房间提供 `room.broadcast` 一类方法，底层仍是现有暂存批次。

协调用邮箱（房间就绪等待者、`requests` 请求邮箱）由 D3 取代；停止信号由会话生命周期与
D1 的独立关闭路径承担。通用 channel 保留为库层流式工具，用于任务间生产者／消费者流水线，
不用于共享状态通信。

### D3／D4 动态访问集合与事务内创建域

两者必须联合设计：已有域不会因为句柄存放在 Catalog 中就获得访问权，“取得或创建房间”
之后加入成员仍需写该房间，换房还需旧房间。拆成“先取得／创建、再加入”两次事务也绕不开
动态集合，因为两次之间房间可能被退役回收，第二次事务仍须校验并重算。

#### D4 依赖状态的访问路径

**R3 已实现**：运行时替代 chat 手写“先读位置、再获取、再校验”的循环，删除 `expected`、`Retry.Changed`。
这一模式在确定性数据库中称为 OLLP（Calvin）。

```text
when "say" (mut account: Account = accounts[id], room?: Room = rooms[account.room]) { ... } else { ... }
```

协议：

1. **解析**：只读解析路径，记录每条路径得到的域**身份**（含世代），不是仅记录键。
   解析不执行用户副作用；路径表达式限于目录查找与字段投影。
2. **获取**：一次取得完整集合的访问权，等待时不持有部分权限。
3. **校验**：在持有权限的状态下重新求值路径，身份不一致即放弃本次尝试。
   目录键被删除后以同名重建，世代不同，校验失败。
4. **重算**：有界次数，超限返回明确错误，次数可配置。路径为空（`?`）进入无该域分支。

**校验范围**：路径校验只证明“路径仍指向同一个域”。账户是否 live、房间成员表是否包含该账户
等业务条件仍在块体内检查（现有 `check_member` 的职责保留），不能由路径机制代替。

**别名**：多条路径可能在运行时解析到同一域（如换房时旧房间与目标房间相同）。
第一版沿用语言参考现行规则：不同绑定可以指向同一只读域；**重复绑定只要涉及写**
（读与写、写与写），就进入声明的别名分支或返回专用结果，由业务处理
（chat 的“已在房间”路径）。调度权限合并不等于引用合法：独占授权下同时暴露同一状态的
`&S` 与 `&mut S`，可能在通过可写绑定扩容容器后使只读绑定的引用失效。
若以后希望把读写别名合并为一个规范绑定，须另行设计编译器借用规则。R3 使用块后的 `alias { ... }`，
只处理末项与有效前缀的写别名；分支只取得前缀引用。可选末项必须声明 `else`，同样只提供前缀。
第一版显式标注路径状态类型，键限于 UInt64 常量／外层投影／先前状态字段，目录为外层弱句柄投影。
Local 在完整注册表访问区间内重算一次即稳定；`max_path_retries` 默认 64，零值拒绝身份变化。

**捕获与重算**：这是新的语言契约，**仅适用于含访问路径、可能重算的 `when`**；
静态访问集合的 `when` 保持现有语义，捕获的 String 等拥有值仍可移入状态或结果。
可重算形式中，捕获在进入首次尝试前打包为独立拥有包，由运行时保留到最终尝试结束，
不借用调用者栈帧；每次尝试以借用形式交给块体，块体需要拥有时显式复制。
重试移入运行时后，重试所需的复制仍然存在，只是从业务代码移到明确的位置，成本须计入预算。

#### D3 事务内创建域

**现状**：域只能在 `when` 外创建并经宿主发布屏障后才对客户端可见，
导致 Catalog 状态机、等待者与宿主侧创建流程。

**方案**：创建作为访问路径的回退分支。

```text
when "join" (mut account,
             mut next: Room = rooms.get_or_stage(name, make_room(name.clone())),
             mut old?: Room = rooms[account.room]) { ... } else { ... } alias { ... }
```

- 解析时键不存在，则计划创建；校验时仍不存在，在本次尝试内暂存新域并独占初始化；
  校验时已被他人创建，则按 D4 重算并获取已有域。
- 新域未发布，不与其他尝试共享，新域本身不需要额外访问权协议。
- **目录协调**：只校验目标域身份不够。两个操作访问不同账户、同时创建同名房间时，
  各自的已有域集合互不冲突，都可能通过“键不存在”检查。因此含创建回退的路径须把
  **目录本身**纳入访问集合并取得写授权：第一版按整个目录粒度授权，以后可细化为按键预约。
  键是否存在、目录容量（`Full`）、目录关闭（`Closed`）与占用（`Occupied`）均在持有该授权、
  到达提交点之前确定；域与目录条目在同一发布区间联合公开，发布区间内不再有可失败的目录检查。
  删除（如空房回收的条件删除）与重建走同一授权，与创建串行化。
  Local 模式下校验与发布本就在同一同步轮次，该规则使两种模式语义一致。
- **所有权**：新域的 Owner 在同一提交中交给目录条目（沿用 `DirectoryHandle.insert_owned`
  的拥有条目规则）；业务状态（如 Catalog）只存键或句柄，不持有 Owner，
  状态根仍保持无资源拥有树。目录关闭或条目按身份删除时关闭对应域。
- 提交点之前失败或取消：销毁暂存域，不留下目录条目；暂存域计入预算。
- 新域使用本次尝试固定的代码版本；代码发布使尝试失效时整体重算，
  因此不再需要宿主的 `refresh` 发布屏障。

**收益**：删除 `next_room`／`init_room`／`open_room`／`fail_room` 四个入口、Catalog 四态、
宿主 `create_room`／`manage_rooms`；宿主不再含业务流程，房间创建可热更新。

**分步**：先交付不含创建的访问路径（替换 `expected`／`Retry`），
再交付创建回退与目录拥有交接（删除房间创建协议）。

### D5 减少候选复制

**重构前**：`Candidates::capture` 对访问集合中每个域完整快照，包括只读域；
在 512 人房间发言会复制整个成员数组。

**第一步：只复制写域（R5 已实现）**。只读域在持有读权限期间受保护地借用，不进入候选；
块体对只读域的访问由编译器保证不写。改动局限在候选捕获与调用路径，消除发言时只读房间的候选复制。
[候选预算对照](../benches/reports/service-concurrency-r5-memory.md)记录内存差异；吞吐仍须按
[基准方法](../benches/README.md) 独立测量。

**第二步（另行评估）：撤销日志**。仅在写域复制仍是瓶颈时考虑。必须覆盖容器扩容、删除、
跨根拥有值移动和失败清理；回滚本身不能依赖可能失败的分配，日志空间须预留。
成本与写入量及日志元数据相关，不承诺与状态规模无关。

### D6 不等待结果的 `when`：以 `branch` 表达，仅定案顺序入队

**默认写法**：不等待结果的需求用现有 `branch { when … }` 表达，不新增语法。
`branch` 登记后主体继续执行；工作归属所在 `scope`，正常退出时汇合，取消时撤回或清理，
域关闭时 `when` 返回 `Closed`。早期设想的“把工作所有权移交给域”所需回答的归属、
调用方退出、关闭顺序等生命周期问题，由此沿用 `scope`／`branch` 的既有规则。
（`background` 仅为设计，且在必要工作结束后取消，可能丢弃通知，不适用于此。）

已知差别：

- **入队顺序**（唯一实质差别）：BoC 保证同一发起者对同一域先后提交的工作按提交顺序执行；
  `branch { when }` 不保证。Local 模式下子任务在主体挂起或进入汇合时才推进，因此

  ```text
  scope {
      branch { when (mut room) { A } }   // 仅登记
      when (mut room) { B }              // 主体直接执行，B 先入队
  }
  ```

  中 B 先于 A 执行；Parallel 模式下两者先后不定。
- **失败传播**：块体内运行时失败经 `branch` 使所在 `scope` 失败；普通域错误仍由 `when`
  以 Result 返回。这是结构化并发的取舍，予以保留。
- **开销**：每个 `branch` 是完整任务（帧、捕获包、登记），重于一个域队列项；按测量决定是否优化。
- **超出调用方生命周期**：`branch` 不能比所在 `scope` 存活更久。移交给域并在调用方退出后
  继续的形式目前没有真实需求，暂不设计。

**D6 定案范围**：是否需要程序顺序入队。若需要，提供在调用点同步入队、由所在 `scope` 拥有
完成的 `when` 提交形式：入队发生在登记时刻，汇合、取消、失败传播与 `branch` 完全一致。
需明确：同步入队失败（排队额度不足、域已关闭）在调用点返回；多线程下“提交顺序”的定义与
BoC 队列合并方式由第 4 节运行协议确定。

### D7 多线程：BoC 运行于共享 worker 池

**修正**：早期评审建议“每核一个单线程执行器、`when` 不跨执行器”，前提是执行器为单线程。
TP 已提供共享 worker 池与受检包，改为 Verona 式：`when` 是调度单位，
目标域全部可用时派往任一 worker 执行。理由：

- 按分片切分会使跨分片换房失去原子性；BoC 无需域与线程绑定，房间间自动并行。
- 状态域协议的“全部取得或一个都不持有”“单调序号”“不插队”正是 BoC 跨线程调度规则。
- `when` 已要求块体同步、捕获为拥有值、状态为无资源拥有树，正好构成可跨线程的受检包。

**三个概念分开**：

| 概念 | 含义 |
| --- | --- |
| 资源所有权 | 哪个任务拥有资源，随移动转移 |
| I/O 注册归属 | 连接注册到哪个共享 reactor；不随执行 worker 变化 |
| 任务调度 | 任务在哪个 worker 执行 |

规则：

- **采用共享 reactor**：连接在其生命周期内保持所属 I/O 驱动，驱动收集就绪事件并通过
  线程安全的等待状态唤醒任务。执行 worker 与注册归属解耦，不通过注销／重注册来迁移任务。
- **跨 worker 转移是必需能力**：连接任务不能因 accept 所在线程而全部固定在同一 worker。
  任务、捕获与资源通过 TP 受检拥有包转移；转移须等待活动 poll 与借用结束，更新唤醒路由，
  不能搬运现有 `Rc`／`RefCell` 或把“可共享 reactor”误当成“任意资源可转移”。
- 由同一资源拆出的 reader／writer 共享一个线程安全连接核心；分别保持方向访问权，
  同方向不得并发执行。连接关闭、借用租约及预算归还参与同一生命周期协议。
- **VM 控制身份共享**：连接任务通过 `Vm.share()` 获取拥有代理并移入 branch。
  `session.run` 的 `&S`／`&T` 和借用静态 race 留在连接所属 worker；不把借用帧跨线程传递。
  函数值与间接目标具备冻结代码证据，控制对象留在控制线程。一般跨 worker 共享借用尚未开放。
- 未来的工作窃取仍受任务／资源资格约束；线程绑定的其他宿主资源仍然 Local。
  共享 reactor 不自动使所有任务可窃取，也不要求立即实现工作窃取。

**`Local` 是实现状态，不是语义限制**。资格分析把未声明 ParallelSafe 的宿主绑定和
状态域操作视为 Local，并沿调用图传播至根入口。逐项情况：

| 能力 | 现状原因 | 处理 | 工作量 |
| --- | --- | --- | --- |
| `println` 等输出 | 实现使用 `stdout().lock()`，错误记录经 TP 已保存／恢复的线程局部状态；已附带 ParallelSafe 证据 | R7a 审计并标注，Show 调用图仍须检查 | 很小 |
| 函数值／间接调用 | R7c 已冻结模块内同签名目标集合 | 传播全部目标效果，未知目标和 Local 依赖拒绝 | 已完成 |
| TCP | R7b 已接入共享驱动、线程安全连接核心和同树拥有转移；Local 计费与共享租约分开 | 已完成；VM／Domains 及跨树资源导入不随之开放 | 中到大 |
| VM 句柄 | 引擎与模块保活仍在控制线程使用 `Rc` | R7c 用同树拥有代理与复制命令桥接；R8 将受检业务操作交给 worker，控制端协调提交 | R7c／R8 |
| Domains／`when` | 注册表为 `Weak<RefCell<…>>`；原子性证明依赖单线程同步轮次 | 按全局尝试序号排队的 BoC 调度：完整访问集一次授权，共享读、独占写；块体编译为 ParallelSafe 入口，发起方 Pending，执行后交回结果包（R8 实际为控制端每注册表一张有序请求表，边界见第 9 节） | 大 |

**准入粒度**：由“根调用树任一 Local 即拒绝整个入口”改为按能力分级，配合上述资源规则。

**多线程下 D1 更必要**：只含 `Disconnect` 目标的提交可逐目标原子投递，溢出经独立路径通知，
不需要跨线程多队列预留；含 `Reject` 目标的提交仍需 D1 所述的协调协议。

### D8 收缩跨挂起提案

“快照 + 读取凭据 + 提案提交”的跨挂起乐观路线不再扩展。读状态、等外部 I/O、再写回的场景
（数据库、支付）改用预留模式：一个 `when` 冻结额度或标记进行中，在 `when` 外执行 I/O，
再用一个 `when` 确认或取消。现有能力保留，预留模式在示例中验证后再决定是否收缩公开接口。

### D9 作用域监督策略

语言增加 `isolate { body }` 失败边界，返回 `Result<T, task.Failure>`；监督、记录和重试在其上组合，
不再给 `scope` 增加策略参数。`scope` 默认 fail-fast 保持不变。隔离区内部任务先取消／汇合并清理，
然后交付失败；外部取消和 ABI 违规继续传播，业务 `Result.Err` 保持普通返回值。
首版仅在挂起函数中使用，禁止控制流跳出隔离区；捕获沿用 branch，结果沿用 scope 的无引用限制。
重启与退避接口另行设计，不在本轮实施。

### D10 确定性模式

Local 执行器增加可配置种子的就绪顺序与外部事件注入，用于重放并发缺陷。
不承诺跨后端或跨版本得到相同调度，仅保证同一构建、同一种子与同一输入可重现。
可控调度的基础设施提前交付，用于复现 D7 涉及的业务操作顺序。它不能单独证明真实多线程
正确性：队列发布、取消交接与内存可见性仍须沿用 TP 的真实 worker 受控交错测试。

## 4. 多线程运行协议（D7 实施前置）

## 6. 目标写法与实际写法

设计阶段的示意：

```text
fn say(id: UInt64, text: String) @suspends -> Result<Unit, ChatError> {
    when "say" (mut account = accounts[id], room = rooms[account.room?]) {
        if !account.route.live || !room.has_member(id) { return Err(ChatError.Stale) }
        if account.balance_cents < 100 { return Err(ChatError.InsufficientBalance) }
        account.balance_cents -= 100
        room.broadcast(event("message", &room.name, id, &text))
        Ok({})
    }
}
```

2026-10-27 重写后 `examples/chat_logic.jk` 的实际写法：

```text
fn say(host: Host, account: domain.WriteHandle<Account>, text: String) @suspends -> Outcome<Unit> {
    when "say" (mut account, room?: Room = host.rooms[account.room]) {
        let member = check_member(account, room)?
        if account.balance_cents < SAY_PRICE_CENTS { send(member, "error insufficient balance\n") }
        else {
            account.balance_cents -= SAY_PRICE_CENTS
            broadcast(room, chat_line(&room.name, member.id, text))
        }
        Ok({})
    } else {
        let member = check_live(account)?
        send(member, "error join a room first\n")
        Ok({})
    }
}
```

相对重构前移除了 `ctx`、`excluded`、`expected`、`Retry`、位置重试循环与捕获复制。路径校验保证 `room`
仍是账户所在的同一个域；live 与成员关系仍由块体检查。可选路径落空时进入 `else` 分支，
换房时新旧房间相同进入 `alias` 分支。`Outcome<T>` 双层 Result 仍保留：外层为访问错误，内层为业务拒绝。

### R2 实施结论

- `outbox.create` 保持 Reject 默认行为；`create_with_policy` 支持
  `Overflow.Reject`／`Overflow.Disconnect(control)`。后者要求同执行器打开的 Reject 控制信箱，
  只保存弱关联，输出关闭／销毁也关闭 control；已销毁输出的句柄仍保留策略，不保留墓碑或所有者。
- 混合批次先完成全部可拒绝检查，再进入无挂起发布区间。Disconnect 目标按整批接收或丢弃，
  溢出标记、输出与 control 关闭不分配资源，唤醒在发布后发生。control 关闭优先于同批对它的投递。
  单批条数／字节和共享存储预算维持原检查；Reject 的错误与 failed_outbox 保留。
- `session.create` 默认连接 Disconnect 输出与独立 control；`Connection.output()` 返回
  `session.Output`（outbox.Handle 的源库别名），业务调用 `output.send`／`output.close`。
  不新增传输包装或改变消息格式，仍由 session.run 的 race 取消阻塞写分支，再调用 on_close。
- chat 删除 `excluded`、淘汰工作表、`slow_client`／`target_member`、停止信箱参数和 max_evictions。
  慢连接不再引起收费／广播回滚与重放，健康收件人先收到本次消息，离开通知随后由普通断线清理发送。
  expected／Retry 和房间创建协议保留给 R3／R4。共享契约和 Account／Room 布局有变化，升级示例需重启；
  新布局内的兼容业务热更新仍按既有契约执行。
- 语言参考已明确部分收件人可能收不到已提交消息；目前状态域保持 Local 执行，不宣称多 worker
  的容量协调已经实现。KeepLatest 与其他 D2 暂存效果不在本阶段交付。
