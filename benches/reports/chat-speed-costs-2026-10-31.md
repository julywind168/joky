# Chat 修复后 speed 对照与每条消息成本（2026-10-31）

基于 `4c45718`（浮点边界已修复）、Cranelift 0.137.1，重新构建并比较 `none`／`speed`。
**speed 有局部收益，但单连接延迟基本不变，多 worker 的收益不一致。**
独立计数显示每条 `say` 有数千次堆分配和浮点环境切换；下一步优先验证纯整数函数中多余的
浮点保护，再对分配做来源归因。本次只提交测量结论，默认优化级别仍为 `none`。

## 干净产物的性能对照

两版使用相同 Rust Release 构建；仅 JIT／AOT 的 Cranelift `opt_level` 不同。
以下为三轮样本中位数，吞吐单位为广播/秒，CPU 为逐样本计算的服务端 ms/广播。

| 房间 / worker | none 吞吐 | speed 吞吐 | 变化 | none CPU | speed CPU |
| --- | ---: | ---: | ---: | ---: | ---: |
| 1 / 1 | 707.1 | 774.2 | +9.5% | 2.0350 | 1.9175 |
| 1 / 4 | 1230.3 | 1335.3 | +8.5% | 2.5900 | 2.4300 |
| 4 / 1 | 1760.0 | 2022.8 | +14.9% | 0.9088 | 0.8500 |
| 4 / 4 | 2566.5 | 2431.4 | −5.3% | 1.3225 | 1.3467 |

前三个配置三轮配对均提高，吞吐范围不重叠；仍只有三个样本，不给跨机器保证。
4 房间／4 worker 三轮配对为 +18.3%、−6.4%、−9.0%，范围重叠，不能认定稳定退步或提速。
单客户端吞吐 1587.1→1605.0（+1.1%），P50 **0.5600→0.5587 ms**，CPU/请求 0.522→0.516 ms。
单客户端吞吐范围分别为 1298～1640、1437～1638，未证实往返延迟改善。
这包含解析、脚本、域事务、队列和回环网络，不是 TCP 单程发送时间。

方法沿用[生成代码优化实验](chat-codegen-opt-2026-10-31.md)，此次全部重新采样：

- Apple M1 Pro、16 GiB、macOS 26.6.2 ARM64、Rust 1.99.0、Python 3.14.6。
- AOT host + JIT script；两版 benchmark 源码快照逐文件一致。没有拆分 AOT／JIT 收益。
- 16 客户端、64 字节正文、1／4 房间 × 1／4 worker，每客户端预热 25 条、每批 250 条、至少 3 秒。
  单客户端为 1 房间／1 worker，每批 5000 条。每次发送后等房间所有接收者收到再继续。
- 三轮顺序 none→speed、speed→none、none→speed，第二轮房间／worker 顺序倒置，每轮矩阵后测单客户端。
- 构建结束后计时，期间没有编译、测试或 profiler。所有 30 个样本验证内容、顺序、余额及正常退出。
  客户端未达到一核饱和；固定闭环负载不代表最大容量。没有重测 Tokio、编译或启动耗时。

## 独立探针：每条 say 的事件数

性能测量结束后，在另一份 `speed` 产物中加入临时计数。通过专用管理命令控制窗口，
排除启动、脚本 JIT、连接、join 和预热。每个配置运行两轮独立进程，各轮测每客户端
0、100、500 条消息；第二轮反序，共 18 个样本。每条消息仍核对内容、顺序及扣款。
用同轮零消息窗口扣除管理命令、余额核对和固定清理开销，再除以广播条数；下表取四个差值样本中位数。
**探针的原子计数会扰动执行，所有探针运行均不用于性能比较。**

| 每条广播的事件 | 1 客户端 / 1 房间 / 1 worker | 16 客户端 / 1 房间 / 4 worker | 16 客户端 / 4 房间 / 4 worker |
| --- | ---: | ---: | ---: |
| 控制桥实际提交 | 2 | 17 | 5 |
| Rust 堆分配（alloc + alloc_zeroed） | 2753 | 7118 | 3583 |
| Rust realloc | 368 | 521 | 401 |
| 堆分配请求字节，约 KiB（不含 realloc） | 406 | 845 | 494 |
| Local Arena 分配尝试 | 28 | 28 | 28 |
| Parallel 存储分配尝试 | 91 | 181 | 109 |
| Buffer 创建 | 48 | 78 | 54 |
| 浮点 enter / restore，各自约 | 3988 | 12946 | 5764 |
| 浮点 reset，约（包含 enter 内部 reset） | 6350 | 20981 | 9273 |

堆分配次数范围分别为 2752.3～2753.0、7115.7～7121.3、3582.0～3584.9，随消息数近似线性。
Rust 分配统计包括运行时及元数据，不含未经过 Rust 全局分配器的 C 库分配；字节数是累计申请量，
不是驻留内存、峰值、泄漏量或实际复制量。Arena、Parallel、Buffer 与全局分配器计数互有包含，不能相加。

实际控制提交严格为 **1 次 VmCall + 每位接收者 1 次 OutboxReceiveBytes**。
普通目录／域操作并非每次都跨这条桥。另计 Local 域入口 poll：单客户端每条消息为
DirectoryLookup 1 次、DirectoryFound 1 次、WhenPaths 3 次；并发时部分 poll 数增加，
这些是含重试／恢复的轮询次数，不是事务数或新的跨线程请求数。

### 已计数的复制

| 每条广播的字节数 | 单客户端 | 单房间 16 人 | 四房间各 4 人 |
| --- | ---: | ---: | ---: |
| 控制桥输入复制 | 838 | 838 | 838 |
| 控制桥返回 Buffer 复制 | 916 | 2093 | 1152 |
| outbox 暂存消息复制 | 78 | 1255 | 314 |
| Buffer::copy_bytes | 1791 | 2968 | 2027 |
| String.clone（2 次） | 86 | 86 | 86 |

这些计数**不是不重叠的全路径复制总量**：String.clone 和部分控制桥返回走 Buffer::copy_bytes，
不可把表中各行相加。正文是 64 字节，广播还带协议前缀／连接 ID；均摊值会有小数。
尚未覆盖所有容器快照、StringBuilder 扩容、allocator 内部 realloc 和内核网络复制。
因此可以确认已计数的消息复制较小，不能据此断言所有复制都不重要。

## 下一阶段选择

1. **先验证纯整数函数中可证明多余的浮点保护。** 当前 `native/float_env.rs::instrument`
   在无浮点值时，只要存在 external call 就插入 enter／restore，即使所有外部目标都已在
   `Effects` 中证明保持环境。可先统计这类函数的实际调用，再只对这类函数省去整组保护。
   未知宿主、间接调用、可能调用用户 Drop 的 helper 和含浮点值的函数继续保留边界；不放宽隔离契约。
   本轮统计的是全部保护调用，尚不知道其中多少满足省略条件，不承诺具体收益。
2. **随后定位数千次分配的主要来源。** Local／Parallel 的直接数据分配远少于全局分配次数，
   值得对 Script 调用准备、域执行准备及收发路径分段归因。代码中确有每次调用重新生成
   `domain_schema`、克隆 `FunctionInfo` 的路径；缓存模块版本内不变的描述是候选，
   但本轮没有分配调用栈，不能把全部差额归给这些函数。缓存必须随热更新换代并保留旧调用生命周期。
3. outbox 批量接收可减少多人广播的控制请求，作为后续候选；需要保留顺序、背压、取消和预算契约。
   共享广播字节要同时考察后续 Buffer 领取与写 socket，否则可能只把复制移到另一层。

事件次数不等于 CPU 占比。以上顺序优先选择范围可控、可单独验证的改动，不依据次数直接预测提速。

## 补测三档编译时间与体积

在上述浮点修复后的代码上增加 `speed_and_size` 对照。官方定义为类似 `speed`，
同时进行旨在减小代码体积的变换，不能理解为速度／体积都保证更优，见
[Cranelift 优化级别说明](https://docs.wasmtime.dev/api/wasmtime/enum.OptLevel.html)。
项目锁定的 0.137.1 源码中，`Context::optimize` 只按 `opt_level != None` 启用 egraph，
所检查的 codegen 路径未发现区分 `Speed`／`SpeedAndSize` 的优化分支；本次两档产物大小也相同。

各档预热一次，再按三档的全部六种排列轮换，共 18 个正式样本。表内为中位数，括号为 min–max。

| 指标 | none | speed | speed_and_size |
| --- | ---: | ---: | ---: |
| AOT 完整构建，秒 | 1.005（0.991–1.018） | 1.035（1.023–1.121） | 1.037（1.011–1.145） |
| 新进程监听就绪，秒 | 0.782（0.779–0.854） | 0.802（0.789–0.824） | 0.796（0.787–0.951） |
| chat 可执行文件，字节 | 8,492,168 | 8,475,640 | 8,475,640 |

相对 `none`，`speed`／`speed_and_size` 的构建中位数增加 **3.1%／3.3%**，约 31／33 ms；
启动中位数增加约 20／15 ms。两种优化档时间范围重叠，未证实彼此有稳定差异。
可执行文件都比 `none` 小 16,528 字节（约 0.19%）；它包含静态运行时，不等同于纯生成代码大小。
本轮没有测 `speed_and_size` 的广播吞吐，不能据编译时间或体积推断其运行速度。

构建计时覆盖 `joky build` 的前端、AOT 代码生成、资源打包及链接；启动计时覆盖加载／JIT 编译
业务脚本和服务初始化，不是单独的 JIT 编译时间。所有样本均使用新进程、独立输出目录、
相同源码与 1 worker；预热后仍受系统缓存影响，不是冷启动实验。计时期间无并行编译或测试。
每次启动在计时结束后核对 welcome、join、4 条广播、余额和正常 shutdown，21 次（含预热）全部通过。

复用上一轮已核对 SHA-256 的干净 none／speed Release 工具，新增同配置的 speed_and_size 工具；
三档项目源码一致。Rust 工具构建不计时，三档仅改变 Cranelift 的生成代码选项。
原始脚本、样本、构建身份、补丁和产物保留于 `target/benchmarks/chat-compile-levels/`。
临时设置已还原，常规 Release 工具／运行时恢复为干净 none 副本并核对哈希。
