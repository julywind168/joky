# 任务完成通知与 worker 定向唤醒（2026-10-31）

本轮以 `5e6d8b9` 为性能基线，调整固定 worker 池的通知路径：

- 每个 worker 使用独立条件变量，任务就绪只通知所属 worker；批量发布完整入队后，
  按轮转分配的目的 worker 各通知一次。关闭及 I/O 驱动失败才通知全部 worker。
- 每个任务使用独立完成条件变量，`Handle::wait` 在任务状态锁下检查 Cleaned 并进入等待。
  结果与 Cleaned 使用相同锁发布，完成后通知该任务的全部阻塞等待者，去掉原 10 ms 轮询兜底。
- 保留任务通知世代、Running → Pending 重检、取消与子树清理屏障，以及各 worker 的最近截止时间。
  共享 reactor、全局队列锁、任务固定归属和浮点保护均不改变。

这是[此前采样](chat-cpu-profile-2026-10-31.md)中无效唤醒路径的修正；
本轮不重新量化系统调用次数，不把旧版每秒唤醒数当作新版测量结果。

## 正确性与附带修复

新增任务池回归通过通道与状态锁协调多个完成等待者，检查正常完成、取消和失败，
并验证完成后到达的等待者立即返回、任务清理只执行一次且预算最终归零。
另一项回归覆盖跨三个 worker 的四任务批量发布、定向就绪通知、定时恢复及全局关闭。
原有 Running 期间通知、迟到通知无效、子树清理和 worker 禁止阻塞等待的测试继续通过。

并行 VM 验证首次出现一个错误分类失败：控制请求准备耗尽预算，预期 ResourceLimit，
实际为 InvalidState（Local control request stopped）。定位到已有的 Call 构造失败路径：
临时 Call 析构先发布兜底错误，遮盖驱动随后发布的真实准备错误。
新增固定预算回归在原逻辑下复现，修复后通过；现在先发布真实准备错误，再清理部分构造对象。
修复单独提交为 `f7b3945`，没有扩大预算或放宽断言。成功请求仍走原准备与执行流程。
候选性能产物包含这一错误路径修复，基线沿用修复前的正常产物；测量负载不注入预算失败。

验证采用 Debug：任务池筛选 13 项通过，其他并行运行时 31 项通过；
并行 VM 首次为 81 项通过、1 项失败，修复后重跑相关控制模块 15 项全部通过。
AOT 并行筛选 22 项通过；独立发布／关闭竞争测试执行 512 轮通过。
没有因错误路径修复重复运行已通过的无关 VM 测试。
`cargo test --test chat -- --ignored` 显式执行的串行／并行真实 TCP 矩阵均通过。
`cargo fmt --check`、`cargo clippy --all-targets -- -D warnings` 和 `git diff --check` 通过。
按本轮约定未运行 `check.sh`、全量测试或无关压力穷举。

## 性能结果

24 个样本均完成协议与退出检查。吞吐单位为广播/秒；CPU 成本为服务器 CPU 时间/广播。

| 房间 / worker | 基线吞吐 | 优化后吞吐 | 吞吐变化 | CPU 成本变化 |
| --- | ---: | ---: | ---: | ---: |
| 1 / 1 | 975.9 | 1,006.5 | +3.1% | -10.5% |
| 1 / 4 | 1,563.9 | 1,573.3 | +0.6% | -10.6% |
| 4 / 1 | 2,341.1 | 2,497.3 | +6.7% | -9.5% |
| 4 / 4 | 3,545.4 | 3,624.2 | +2.2% | -11.3% |

12 组新旧配对的每次广播 CPU 成本全部下降；四房间／单 worker 为 0.740→0.670 ms，
四 worker 为 0.956→0.848 ms。相比吞吐，CPU 成本改善方向更一致。
单 worker 的三组配对吞吐均提升；四 worker 两种房间配置均出现过反向波动，
不能据吞吐中位数的小幅增长宣称稳定的多核吞吐提升。
四房间／四 worker 吞吐范围为基线 3,219–3,664、候选 3,486–3,880 广播/秒；
该配置的 P99 中位数为 6.87→6.60 ms。
本轮结论是降低无效通知路径的 CPU 消耗，吞吐仍受其他路径限制。
这里使用同轮基线，不将上一轮不同时间的吞吐拼成增幅。

## 测量方法

Apple M1 Pro、macOS ARM64，正常 Rust Release，生成代码 `speed`。
基线复用上一轮浮点边界优化后的工具与应用快照，校验编译器／静态库与构建记录的哈希。
候选重新构建，相同 chat 源码逐文件哈希一致。16 客户端、64 字节正文，
每客户端预热 25 条，每批 100 条；四房间至少 20 秒，单房间至少 5 秒。
每配置三个独立进程样本，交替旧→新、新→旧、旧→新，第二轮反转配置顺序。
吞吐和 CPU 成本均取样本中位数；CPU 成本先按每广播归一化。
测量保留协议内容、顺序、扣费及退出检查，不与构建、正确性测试重叠。
闭环负载不代表最大容量，本轮没有重测 Tokio。

原始样本、构建快照、验证日志保留在 `target/benchmarks/chat-targeted-wakes/`，不提交 Git。
