# Chat 历史基线复测（2026-11-06）

当前版本 `4f67af94` 与 2026-10-31 保留版本 `471185f` 的历史记录相比，12 组配置中有 10 组吞吐下降，
每条广播的服务器 CPU 成本全部升高。旧二进制与原始样本已不可用，本轮没有重建旧版本同场复跑，
因此这些差异不能直接认定为代码回归，也不能归因于某一项近期改动。

## 配置与结果

同一台 Apple M1 Pro / macOS ARM64，Rust Release、生成代码 speed，AOT host + JIT 业务脚本。
16 客户端，1／4 房间 × 1／2／4 worker × 64／1024 B 正文；每连接预热 25 条，每批 100 条，
每个样本至少 10 秒，每组 3 个独立服务进程，共 36 个样本。轮换 worker 顺序，第二轮反转房间和正文大小顺序。
构建完成后才开始计时；沿用历史矩阵的不写逐消息 CSV 模式，保留内存延迟统计和协议校验。

## CPU、延迟与限制

- 每条广播的服务器 CPU 时间增加 **8.7%–37.4%**。单房间／4 worker 最明显：
  64 B 为 **1.204 → 1.654 ms/广播**，1024 B 为 **1.229 → 1.655 ms/广播**。
- 同配置的 P99：64 B 为 **10.09 → 11.71 ms**，1024 B 为 **10.82 → 14.58 ms**。
  四房间的 P99 有升有降，不能概括为所有配置尾延迟变差；这里的 P99 指样本内 P99 的中位数。
- 当前各组采样最大 RSS 的中位数为 **65.9–68.2 MiB**，客户端 CPU 为 **0.45–0.71 核**。
  历史矩阵未保留可比 RSS，不能判断内存变化。
- 三轮存在明显波动，例如 64 B／4 房间／2 worker 为 **3896–4510 广播/秒**。
  历史对比没有控制两次测量之间的系统负载、温度与工具链差异；闭环负载也不代表最大容量。
  下一步应重建旧版本交错复测，再针对单房间／4 worker 采样定位 CPU 成本增长。

36 个样本均通过消息内容、顺序、扣费和正常退出校验。本轮未重测 Tokio，未跑全量检查，未修改生产代码。
构建身份、运行配置、逐样本数据及完整对比保存在忽略的 `target/benchmarks/chat-2026-11-06/`，
其中 `measurement.json` 记录配置，`comparison.csv` 保存全部 CPU、延迟和 RSS 指标；这些本地产物不提交 Git。
