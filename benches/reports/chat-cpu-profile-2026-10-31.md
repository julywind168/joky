# Chat CPU 与等待路径采样（2026-10-31）

本轮以 `1c76715`（运行时实现仍为 `9ca683f`）为基线，定位下一步优化入口。
没有采用新的运行时优化。采样发现，长时间运行时的共享存储索引增长，比继续减少
schema 字符串分配更值得优先处理。以下是诊断数据，不是新的无探针性能对照。

## 共享存储索引

`parallel/storage.rs` 的 16 个索引桶各自使用按地址排序的 `Vec<Location>`。
分配插入、释放删除会搬移相邻记录，而且发生在桶锁内；桶内查找是对数复杂度，
插入和删除的搬移成本仍与位置及桶长有关。

同一诊断产物的四房间／四 worker 长窗口中，`Location` 搬移占 Running CPU 样本的
52.4%；分成两秒窗口后，占比从 22.4% 上升至 63.9%（最后不足两秒的尾段为 64.7%）。
四房间／单 worker 长窗口也观察到增长，总占比 34.5%。
另一次四 worker 短窗口仅为 4.3%，随后独立的五秒 `sample` 也显示较低的搬移量。
这说明短窗口容易遗漏退化，且不同进程的表现有明显差异；不能把单次低占比当作成本上限。

独立计数探针在现有锁内累计分配、删除、搬移条目数与桶长高水位，不改变索引算法。
每客户端预热 25 条，随后运行至少 20 秒；退出时读取索引尚未由存储根析构回收的条目。

| 房间 / worker | 测量消息数 | 退出时仍登记的条目 | 累计搬移条目数 |
| --- | ---: | ---: | ---: |
| 4 / 4 | 60,800 | 61,387 | 1,011,516,406 |
| 4 / 1 | 41,600 | 42,187 | 556,330,845 |

两次剩余条目数都等于测量消息数加 587（包括 400 条预热消息及连接、控制路径）。
这是存活登记随消息数量增长的直接证据；最终存储根析构仍会释放记录和分配，
不能据此称为进程退出后仍不归还的泄漏。计数运行并非每次都显示吞吐随时间下降，
具体搬移量还取决于分配地址和插入／删除位置，探针产物也会改变布局。

补充尺寸和分配栈探针运行 43,200 条测量消息后，剩余 43,787 条记录，其中
43,736 条为 248 字节，51 条为 32 字节。248 字节与当前 `Buffer` 头一致；
捕获的分配栈包含 `Buffer::slice → Buffer::view → Arena::allocate`。
源码给出具体入口：TCP 行解码调用 `String.from_utf8`，后者每次用
`input.slice(0, length)` 创建全范围视图；`Buffer::view` 明确把非拥有头保留到根 arena
结束，没有在 UTF-8 校验完成时回收。该路径与每条消息多留一个头的计数一致。

分配栈是在 shard 存活条目跨过 1024 时抽样，并没有为所有残留地址追踪完整生命周期，
所以尺寸分布不能单独证明每个残留头都来自这个调用。下一步应先用最小用例和修改前后
计数验证此路径：全范围只读视图能否安全复用已有头，或将临时视图纳入正确的回收边界。
同时检查其他切片、迭代器元数据的同类保留；不要先靠扩大桶数掩盖增长。

## 其他热点与等待路径

下表以目标进程处于 Running 状态的采样权重为分母。浮点项为环境读写函数叶节点，
同步项仅含 `psynch_*`／`ulock_*` 系统调用叶节点；它们不是墙钟阻塞时间。
分配器项不含上层预算与存储登记逻辑。热点分类没有覆盖全部 CPU 时间。

| 采样配置 | 有效 CPU 窗口 | Location 搬移 | 浮点环境读写 | 同步系统调用 | 分配器 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 4 房间 / 1 worker，System Trace | 3.515 s | 4.0% | 19.2% | 8.0% | 12.2% |
| 4 房间 / 4 worker，System Trace | 2.012 s | 4.3% | 16.0% | 22.6% | 13.5% |
| 1 房间 / 4 worker，Time Profiler | 20.645 s | 2.5% | 17.9% | 18.7% | 12.3% |
| 4 房间 / 1 worker，Time Profiler | 20.628 s | 34.5% | 12.5% | 5.3% | 9.8% |
| 4 房间 / 4 worker，Time Profiler | 20.595 s | 52.4% | 7.0% | 13.7% | 5.3% |

索引搬移占比上升会压低其他项的相对比例，不代表浮点与唤醒的绝对成本已经改善。
四 worker 的短窗口中，`domain_schema` inclusive CPU 约 1.35%，
`value_schema` 约 0.46%；两者可能重叠。这里只采了基线，不能用它断言上一轮
[域资格校验实验](chat-schema-check-2026-10-31.md)的负向样本究竟由什么引起。

System Trace 的线程状态区间裁剪到同一实际 CPU 窗口后：

- 单 worker 样本：worker 处于 Running 的时间约占墙钟 94%，控制线程约 63%。
- 四 worker 样本：各 worker 约 53%–63%，控制线程约 88%；扩展后的限制不只是 worker 计算。
- 主线程只等待根任务完成，却分别出现约 1.43 万／2.05 万次 `psynch_cvwait` 每秒。
  `sample` 调用栈定位到 `Handle::wait`；它与 worker 队列共用条件变量，
  `Task::wake` 的 `notify_all` 会让这个尚不能完成的等待者反复醒来。

这些短窗口只支持路径归因，不构成最大容量或扩展性结论。系统调用时长包含运行、
可运行与阻塞区间，不能直接等同于等待时间，也不能与线程状态时长相加。

## 后续顺序

1. 先处理 `String.from_utf8` 全范围切片头的生命周期，用固定连接、持续消息的用例验证存活条目稳定，
   再复测长窗口与不同 worker 数。若消除增长后搬移仍显著，再评估索引结构。
2. 分离根任务完成通知与就绪队列通知，之后评估按 worker 唤醒。
   不能直接把 `notify_all` 换成 `notify_one`：独立 worker 队列下可能唤醒错误的等待者。
   修改必须覆盖取消、关闭、截止时间与丢唤醒边界。
3. 浮点环境读写仍有优化价值。可试验真实状态相同时省去写寄存器，保留控制位、状态位及
   宿主边界的完整语义；是否获益取决于额外读取／分支成本，需独立对照。
4. schema 纯校验和预算小分配暂排后面；减少调用／分配次数需要落实为端到端收益。

## 方法与验证范围

Apple M1 Pro、macOS 26.6.2 ARM64、Rust 1.99.0、Cranelift 0.137.1，生成代码为 `speed`。
沿用 `chat-workers.py` 的 AOT 宿主加 JIT 脚本、16 客户端、64 字节正文、内容／顺序／扣款／
退出校验。采样在预热之后开始；请求持续到采样结束。各次运行使用同一份诊断应用。
性能归因显式使用 Release：运行时增加 `debuginfo=1`、frame pointers 并保留链接符号，
没有改变运行时算法。JIT 帧有部分未解析地址，因此不强行给所有上层调用命名。

使用 macOS `xctrace` Time Profiler／System Trace，随后用五秒 `sample` 核对调用栈。
System Trace 请求采集 12／20 秒，但导出的目标 CPU 有效窗口只有约 2／3.5 秒；
线程状态和系统调用按实际窗口裁剪，另补约 20 秒的 Time Profiler 长窗口。
系统导出按目标 PID 过滤，未将其他进程的数据计入结论。构建、导出解析与采样分开执行。
采样器、符号与计数探针都会扰动执行，故不把这些运行的吞吐作为优化收益。

所有采样负载及独立计数负载完成协议校验。探针只在本地临时构建，恢复源文件与正常工具后
仅提交报告和导航；没有运行全量检查或压力测试。原始 trace、导出、脚本、探针补丁与工具
快照留在 `target/benchmarks/chat-profile/`，不提交 Git。
